# AWS Pricing Calculator Parity Test（公式入力・料金一致検証）

最終更新: 2026-10-13

## 1. 目的・位置づけ

公開サイト `https://nobleneet.github.io/AWSPricingCalculator_forTAE/` の全収録サービスについて、AWS公式 `https://calculator.aws/` を独立した比較対象として、**双方の設定項目の対応・欠落・入力意味**と、同等入力による月額金額、コンポーネント内訳および**各パラメータの変更による金額の変化量**を実ブラウザGUIで検証する最上位ブラックボックス受入試験である。

入力対応の判定と料金比較の判定は独立して記録する。本ツールに存在する項目だけを試験しても、公式側の項目欠落を含むParityの合格とはしない。この規則はEC2を含む全収録サービスへ適用する。

この試験は通常のunit / Golden / E2E / Price DB validationを置き換えない。AWS公式Calculatorは実装を比較する外部の基準であり、差額の存在だけで自作側の不具合と断定しない。AWS Public Price Listが単価の正本であることは `docs/SPEC.md` と `docs/PRICING_ARCHITECTURE.md` に従う。

## 2. 実行許可と隔離（必須）

- **ユーザーがこのParity Testの実行を明示指示したセッションでのみ実行**する。過去の許可は引き継がない。
- push / PR / merge / onboarding / re-onboarding / price-update / build / Pages deploy / scheduled jobをトリガーに自動実行しない。
- `npm test` / `npm run validate` / `npm run test:e2e` / 通常CIの依存に組み込まない。GitHub Actionsのscheduled / automatic workflowを作らない。初期段階ではworkflow_dispatchも不要。
- 結果ファイル生成、ケース設計、仕様編集、修正指示書閲覧は実試験の実行許可を意味しない。
- 運用環境はユーザー管理下のCodex CLI＋利用可能なブラウザ操作環境。LLMやブラウザ操作手段の存在は起動前に確認する。単なるCLI権限昇格をGUI操作能力とみなさない。
- **検証担当はアプリ・価格DB・公式サイトを修正しない。** FAILの検出で自動修正せず、修正・再検証も別途ユーザーの明示指示を要する。
- 通常のサービスオンボーディング完了ゲートには追加しない。オンボーディング時に従来のGolden/E2Eは実施する。

## 3. 正本・対象範囲・バージョン

- 対象はローカル版・`mock/`ではなく**実際に公開されているPages**。ローカルのGit cloneが古くても構わず、古いコードやcatalogから公開仕様を推測しない。
- 毎回公開版のサービス一覧を取得し、各サービスについて**公式側と公開版側をそれぞれ独立して**Profile、Region、Primary/Advanced/conditional入力、selectorの候補、usage単位、依存関係、料金内訳をGUIから棚卸しする。各側の項目に安定IDを付与する。公開版のDefinitionや既存ケースから公式側の項目一覧を生成しない。
- GitHubの最新mainのサービス定義・coverage・仕様書は補助的な調査資料としてよいが、実測結果の代替や期待金額の生成には用いない。
- 実行ID、UTC/JST日時、公開URL、可能なら公開Price DB/build IDとPages commit SHA、ブラウザ環境、サービス一覧スナップショットを保存する。
- 実行途中で公開ビルドが切り替わったら別スナップショットとして分離し、混在ケースの比較を停止・再測定する。識別できない場合はリスクを明示する。
- 検査Regionは正式対応Regionと公開画面の実対応範囲に基づく。東京のみを暗黙に全Region代表にしない。

## 4. AWS公式サービスURLの発見

ユーザーが公式URLを提示した場合は、そのURLを参照先として実画面を確認する。別画面への変更が必要な場合は理由と比較範囲を記録し、提示URLで未確認の範囲を確認済みとしない。URL未提示の場合は以下の順で発見する。

1. 前回確認済みの `service-url-registry.json` を読み、ブラウザで有効性を再確認。
2. オンボーディング資料や最新リポジトリのサービス別ドキュメントを確認。
3. AWS公式Calculatorのサービス選択画面から自動検索。
4. AWS公式の公開ページから対象サービス作成画面を特定。
5. 実際にレンダリングされた画面のタイトル・入力項目が対象に対応することを確認し、URL・確認日時・対応serviceIdを登録。

`#/createCalculator/` 以下が内部serviceIdと同じとは限らない。文字列連結だけで確定しない。URL不明は `BLOCKED` として記録し、他サービスを継続。ユーザーにURLを求めるのは自動探索が尽きた場合のみ。

registryにはservice ID、実際の到達URL、画面タイトル、確認日時、言語、Region/Profile等の観測条件、証跡、`comparisonScope`を保存する。別サービス画面による組み込みComponentの比較は部品比較として登録し、親サービス全体の項目・総額一致を証明したと扱わない。実行ごとのregistryを結果ディレクトリに保存する。

## 5. ケース生成と網羅性

### 5.1 双方向の項目照合（ケース生成前に必須）

1. 公式側の主要・詳細・任意セクションを展開し、Profile、親selector、Region等の条件変更で現れる項目も棚卸しする。折りたたんだ初期画面だけを全項目一覧にしない。調査できない条件・選択肢と理由を記録する。
2. 公開版側も同様に独立して棚卸しし、双方の**和集合**から`field-correspondence.json`を作る。公式だけにある項目、公開版だけにある項目も必ず行として残す。
3. 項目名だけでなく、入力意味、単位、候補、初期値、範囲、条件付き表示、依存関係、課金Componentとの対応を確認する。1対多・多対1や単位換算を許容するが、変換式と同等条件を記録し、意味の異なる入力を名前だけで対応付けない。
4. 各行を次の分類へ割り当て、入力対応の判定、根拠、証跡、関連ケースIDを保存する。

| 分類 | 内容 | 入力対応の判定 |
|---|---|---|
| `MATCHED` | 双方に同等入力があり、候補・初期値・条件等の差も確認済み | 対応範囲が整合する場合のみPASS |
| `SPEC_EXCLUDED` | 対象外購入プラン等、現行正本仕様が明示的に認める除外 | 根拠文書・節・理由を必須とし、PASSには数えない |
| `MISSING_LOCAL` | 公式に存在し、仕様上必要な対応入力が公開版にない | FAIL。金額測定できなくても欠落ケースを作る |
| `MISMATCHED` | 入力意味・候補・初期値・条件等が不整合 | 仕様根拠のない不整合はFAIL。認められた仕様差は明記する |
| `LOCAL_ONLY` | 公開版だけに存在する独自入力 | 正本仕様の根拠と公式への換算・比較範囲を記録。同等条件を確認できればその範囲でPASS、仕様上の独自項目は除外を明記。仕様外の不整合はFAIL、未確認はBLOCKEDまたはINCOMPLETE |
| `UNCONFIRMED` | アクセス・操作・調査未完了等により確認できない | BLOCKEDまたはINCOMPLETE。理由と未確認条件を必須とする |

「On-Demand固定」はReserved / Savings Plans / Spot等の購入プラン選択を除外する根拠であり、通常使用量、storage、monitoring、data transfer等を一括して除外する根拠にはしない。その他の省略には項目ごとの現行仕様の根拠が必要である。Definitionにないこと、coverageでignoredであること、既存試験がPASSであること、実装が難しいことだけを除外根拠にしない。採用規則は`docs/SERVICE_ONBOARDING.md`を参照し、正本間の解消不能な競合は仕様問題として記録する。

項目欠落と料金測定不能は別判定とする。`MISSING_LOCAL`の料金比較がNOT_COMPARABLEでも、入力対応のFAILは維持する。仕様外の機能を検証担当が推測で実装要件へ追加することも禁止する。

### 5.2 料金ケースとカバレッジ

**全サービス・全Profile・全料金関連入力項目について、少なくとも一つの有効な基準ケースと、当該項目の変更による差分検査を必須**とする。

§5.1の仕様除外は料金測定対象から除外できるが、対応表・除外集計に保持する。入力欠落・不整合・未確認については測定を捏造せず、個別ケースに判定と理由を保存する。公式側の項目を試験母集団から消さない。

- 数値入力: 0が有効なら0、最小値、一般的な値、大きな値、課金境界の直前・境界・直後、単位換算境界。公式画面と自作画面双方に有効な値を使う。
- selector: 全候補を棚卸し。有限で小規模なら全候補を試験。大量候補はSKUファミリー・課金モデル・OS/architecture/size等の意味が異なる代表集合を選び、**省略した候補と理由を必ず列記**する。
- 条件付き項目: 親条件で表示させて個別変更を実測する。Profile別・Region別の条件を含む。
- 相互作用: 価格に関係する依存条件、コンポーネントのon/off、料金モデル切替、境界、ペアワイズ等の代表組み合わせを追加する。
- 金額が変化しないはずの入力も、不変となることを検証する。
- **全項目の検証は必須だが、全選択肢の全組み合わせ総当たりは要求しない。** ただし項目の未検証をPASS扱いしない。
- 全ケースを機械可読に保存し、双方の項目ID・対応表・Profile・Regionから関連ケースへ逆引きできるcoverage matrixを生成する。ケース0件の欠落・未確認項目も表示し、既存ケース一覧だけから分母を作らない。
- 実行のたびに全サービス・全項目のカバレッジを再棚卸しし、料金比較も再実施する。過去結果は今回のPASSに流用しない。

## 6. GUI操作と測定

自作側と公式側の両方をJavaScript描画後の**実画面**で操作する。Playwright/コンピュータ操作ツールで入力・クリック・表示読取してよいが、内部関数、API直接呼出、Price DB、localStorageや内部状態の直接書換えを合格証拠・GUI操作の代替にしない。

各ケースで:
1. 新規の独立した見積状態を用意し、双方のRegion、Profile、On-Demand、構成、使用量、単位、月間時間等を等価に設定する。
2. 基準値で再計算完了を待ち、実際に**表示された**月額合計・取得可能な内訳・警告・単位・スクリーンショットを保存する。
3. 対象パラメータを変更し、他の設定値が変わっていないことを画面で確認してから再測定する。
4. 公式側も同じ基準値・変更後値で操作する。表示更新が完了しない場合は推定値で補わない。
5. 双方の絶対金額、コンポーネント、変更前後差分、方向（増加/減少/不変）、比例・単価切替・境界を比較する。
6. 必要なら独立ケースを再実行し再現性を確認する。

公式Calculatorのログイン要求、CAPTCHA、アクセス制限、操作不可状態があれば回避手段を捏造せず `BLOCKED` にする。操作の自動化が不安定な場合は実際に許可された操作ツールを使用し、無人で処理できなければ制約を報告する。

## 7. 等価性・判定規則

比較前に双方の課金前提の等価性を検証する。本アプリはUSD、On-Demand、割引/税/為替なしを基本とし、Tier・無料枠・請求履歴依存料金の対応範囲は実行時点の`docs/SPEC.md`と参照先のサービス別契約に従う。過去の一律非対応という前提を流用しない。公式側で条件を等価に設定・分離できないときは比較できるコンポーネントだけ個別検証する。

以下は料金比較の判定であり、入力対応の判定は§5.1に従う。

- `PASS`: 同等条件の総額・対応内訳・パラメータ差分が許容差内で一致し、金額変化の方向や課金意味も整合。
- `FAIL`: 同等条件で有意な金額差・変更量差・料金コンポーネント誤選択・変化方向不一致などが再現。
- `BLOCKED`: URL/アクセス/GUI/ツール制約等で試験不能。
- `NOT_COMPARABLE`: Free Tier/Tier等の仕様差・入力の非等価性により正当な比較が成立しない。
- `INCOMPLETE`: 実施対象だが未完了。未検証/省略も明示。

USD月額表示額の初期絶対許容差は**0.01 USD**。完全一致と丸め許容一致を区別する。表示精度が異なる場合は根拠付きで許容差を調整し、差額を隠さない。相対差だけで小額ケースの不整合を合格にしない。単価は可能なら高精度の表示・公式資料でも照合するが、GUI以外の情報だけでPASSにしない。

合計が偶然一致しても、対応する内訳や課金意味が異なる場合はPASSにしない。0 USD同士の一致でも理由を検証する。差額の原因を特定できない場合は憶測を事実として報告しない。

サービス全体のParity PASSには、対象範囲の入力対応が確認済みで仕様外の欠落・不整合がなく、必要な料金ケースもPASSであることを要求する。入力または料金にFAILがあれば全体はFAIL。FAILがなくてもBLOCKED / INCOMPLETE / NOT_COMPARABLEが残る範囲を全体PASSにしない。仕様除外を含む場合は「仕様除外を除く範囲でPASS」と対象範囲を明示する。部品小計のPASS、独立Price List検証、Golden、翻訳テストのPASSで入力欠落や未測定の料金を相殺しない。

## 8. 中断・再開・負荷管理

- 各ケース完了時にケースJSON、スクリーンショット参照、入力、結果、実行状態を**即時保存**。集計は随時再生成可能にする。
- 中断後は同一実行ID・同一公開ビルド・同一料金前提に限りPASS等の実測結果を保持し、未完了ケースから再開。ビルドや公式料金前提が変更されたと判断した場合は影響ケースを再実行。
- サービス単位のアクセス失敗でも他のサービスを最後まで続ける。リトライは有界（例: 1操作3回まで、状況に応じ明示的に調整）、原因/回数を記録する。
- 初期実行は過度な並列を避け原則逐次操作。公式サイトへの負荷を抑え、レート制限・規約・CAPTCHAを迂回しない。
- 停止して再起動できるようにチェックポイントを維持する。試験失敗1件で全体停止しない。

### 全ケースの個別実測記録（PASS含む必須）

- `cases.json` はケース計画・入力定義の一覧であり、`cases/<service-id>/<case-id>.json` は**各ケースの実行結果**とする。両者は安定したcase IDで対応させる。
- PASS、FAIL、BLOCKED、NOT_COMPARABLE、INCOMPLETEの**全ケース**で個別JSONを作る。未実施の場合も理由、最後の進捗、再開に必要な情報を保持し、未測定金額を推測で埋めない。
- 各JSONには少なくとも、case ID、service ID、Profile、Region、検証パラメータ、双方の項目ID・対応表の行ID、`comparisonScope`、`inputVerdict`、`pricingVerdict`、全入力値・単位・条件付き項目、対象URL、実行日時、公開ビルド識別子、テスト状態・判定理由、変更前/後の双方のGUI実測総額と取得可能な内訳、双方の変化量、金額差・許容差、警告・制約、証跡相対パスを記録する。測定不能な欄はnullと理由で表す。項目欠落ケースでは価格未測定でも`inputVerdict: FAIL`を保存する。
- FAILの`failures/<case-id>/comparison.json` は、この個別記録を参照または矛盾なく派生させる。二重に記録した値が食い違わないことを検証する。個別修正指示書から個別ケースJSONへ相対リンクを付ける。
- `summary.json`/`summary.csv`/`summary.md`、`coverage-matrix.json`は双方の項目棚卸し、対応表、個別ケース記録から再生成可能にする。全対応表行が集計と関連ケースへ辿れることを確認する。途中再開や再集計によって以前のPASS記録を誤って今回の実測に混在させない。
- 前回実行との差分を追跡できるよう、同じcase IDと等価な入力条件を維持し、公開ビルド・料金前提が異なる比較には注記する。過去のPASS値で今回のGUI計測を省略しない。
- 大容量の画像はJSONに埋め込まず、相対ファイルパスで参照する。

サービス別に公式側・公開版側の全項目数、各対応分類の件数と一覧、入力対応の判定、料金比較の判定、Profile・Region範囲、ケース総数、PASS/FAIL/BLOCKED/NOT_COMPARABLE/INCOMPLETE、最大金額差、証跡リンクを報告する。公式側の確認率は「対応分類を確認した公式項目数 / 公式全項目数」、料金検査率は「測定済みの対象項目数 / 仕様除外以外の料金検査対象項目数」を分子・分母付きで示す。根拠を確認した除外と確認済み欠落は前者の確認数に含めても、対応済み・料金PASSには数えない。1対多・多対1の対応でも各側の項目IDを重複計上しない。棚卸し自体が未完了なら全項目数を確定済みと表現せず、未確認条件を表示する。

結果ディレクトリ一式を元セッション・一時checkout以外から追跡できる保存先へ保管し、`manifest.json`と完了報告に保存先・取得手順を記録する。保管未完了は残課題として明示する。画像をGitへ自動追加する必要はないが、集計・元ケース・対応表・URL記録・証跡の参照を失わせない。

操作手順・安定locators・公式URL対応は次回の実行効率化のため保存・再利用できるが、実画面で毎回再確認し、金額の再計測は省略しない。

## 10. NGケースを修正指示書として出力（必須）

各`FAIL`ケースについて、**別Codexセッションがファイル一つを読めば原因調査から修正と回帰確認に着手できる、自己完結した命令形の `fix-instructions.md`** を生成する。

入力欠落・不整合のFAILも対象とする。公式項目・表示条件・欠落箇所・対応表・仕様根拠・証跡を記録し、測定できない金額はnullと理由で表す。下記の変更前後額を捏造せず、GUI上の欠落再現と期待する入力対応を修正担当へ渡す。

必須内容:
1. ID、サービス、Profile、Region、不具合概要、重大度と影響範囲
2. 公開サイト/公式URL、計測日時、公開ビルド識別子
3. 全入力値、変更前・変更後のGUI再現手順（単位とデフォルトも含む）
4. 双方の実測合計/内訳/差分/変化量と許容差、判定理由
5. 期待動作、添付証跡の相対パス、機械可読comparison.jsonへの参照
6. 観測済み事実と**未検証の原因仮説を明確に区別**した調査方針
7. 調査対象（Service Definition / Mapping / Price DB / Billing Transform / UI等）と根本原因の確定要求。未確認のファイル名や関数名を断定しない
8. 既存`AGENTS.md`、`docs/SPEC.md`、`docs/PRICING_ARCHITECTURE.md`、`docs/PRICING_MAPPING_ARCHITECTURE.md`、`docs/SERVICE_ONBOARDING.md`、`docs/ONBOARDING_PROMOTION_QUEUE.md`への参照
9. 修正方針: 金額をハードコードしない、Price DB手編集禁止、他サービスへの影響とvalidation scope保全、根本原因が不明なら先に調査する
10. 修正に必要なnarrow test / Golden / E2E / 全体検証 / 公開反映後の公式GUI再比較
11. 完了条件と、権限・公開障害などによる残課題報告方法
12. **「本書を修正依頼として扱い、最新版リポジトリとAGENTSを読み、原因調査→安全な修正→検証→必要なPR/公開確認まで進めよ」**という実行指示

`fix-all.md` は全FAILの一覧、重大度、同一原因の可能性があるクラスター（仮説と明記）、推奨修正順、個別指示書への相対リンク、必要な回帰範囲を含む。

`BLOCKED`/`NOT_COMPARABLE`/`INCOMPLETE`にも調査・再実行用の `investigations/<case-id>/instructions.md` を出すが、実装バグの修正指示と区別する。

**追加の汎用「NG修正ガイド」は作らない。** 修正工程の共通ルールは既存`AGENTS.md`と関連仕様書が正本であり、個別NG指示書がそれらを参照する。実測なしで修正内容を決め打ちせず、修正担当が最新mainを確認すること。

## 11. 完了報告・実行終了

- 双方の独立棚卸し、和集合の対応表、公式だけ・公開版だけの項目、仕様除外の根拠、全項目の関連ケースと判定または未実施理由、入力・料金の別集計、各FAIL指示書、結果の保存先が揃ったことを確認する。
- FAILがゼロでも`summary.md`と`fix-all.md`に明記。未実施/比較不能をPASSとして集計しない。
- 検査率、対象サービス・Profile・Region、結果内訳、最大差異、修正指示書一覧を報告する。
- 検証担当によるソース改修・自動再テストは実施しない。結果報告で終了する。
